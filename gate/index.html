A guard sits between a language model and any side effect. It refuses what it cannot positively recognise, and it names the reason. This page posts your proposal to a live guard and shows you the answer. No model is called and no account is needed.

      Check the receipt yourself

      The receipt carries the exact bytes the digest was taken over. Paste it here and this page recomputes the hash. Or ignore this page entirely and run the same thing in a terminal, because the hash is plain SHA-256 over those bytes.

      What this shows, and what it does not

      • It shows the default. A proposal the guard cannot positively recognise is refused, the refusal carries a reason code, and the decision carries a digest over the bytes. A conformant proposal passes, which matters: a guard that refuses everything proves nothing.
      • It is a demonstration policy, not the production one. The action vocabulary here is a demonstration set. The policy that governs the real runtime is not published, is not in this page, and cannot be read from it. What is shared is the mechanism, which is already described in the deck and the lessons.
      • Any public gate can be queried. Someone determined could map whatever policy sits behind it, one proposal at a time. That is exactly why this one runs a demonstration policy rather than the real one.
      • It does not judge whether a proposal is wise. The guard checks shape and scope. A conformant, correctly scoped proposal that is strategically wrong still returns ALLOW. The checker that would judge intent does not exist yet.
      • A receipt is not a certificate of truth. It certifies that this policy was applied to these bytes, nothing more. Consistency is not wisdom: a system can be perfectly consistent about a wrong premise.

      Each submission is one request to a backend function. Nothing is stored, no model is called, and no data leaves the guard except the answer you see.
