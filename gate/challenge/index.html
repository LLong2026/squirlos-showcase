THE CHALLENGE · LIVE GUARD · NOTHING BEHIND IT

Try to break the guard.

This is not the runtime. There is nothing here to take, no system behind the check, no account, no model. It is one guard, and the question is narrow: can you get an ALLOW on something it promises to refuse. Name tricks, type tricks, scope tricks, whatever you like. Every answer names its reason, and every answer comes with a receipt you can hash yourself.

What the guard promises

A finding is a broken promise. These are the four it makes.

  1. It refuses what it cannot recognise. An action it does not know is denied, never waved through.
  2. It refuses anything that declares itself destructive, however that declaration is spelled. Not just the boolean true.
  3. It refuses a proposal missing a field its action requires, and a write that does not name the app it intends to touch.
  4. It refuses an oversized payload. Sixteen kilobytes is the limit.

      What counts as a finding

      • A false ALLOW is a finding. You broke one of the four promises above and the guard said ALLOW anyway. Keep the receipt: it names the exact bytes that were decided, so a finding can be reproduced instead of described.
      • A false DENY is not a security finding, but it is worth knowing, because a guard that refuses too much gets turned off by the people who have to live with it. If you find one, it is still interesting.
      • The known boundary, stated up front so nobody thinks they discovered it. Intent that lives inside the payload is not read. A write whose payload says DELETE FROM ... is a write, and it will be allowed if the write itself is well-formed and scoped. That is not a bug in this guard, it is the edge of what any check on shape and scope can do. It is the unsolved part of the problem, and it is the reason this page exists rather than a claim that the problem is solved.
      • Matching is exact by design. A known action in a different case is treated as unrecognised and refused. Refusing a near-miss is the fail-closed choice: the alternative is guessing which variant someone meant.

      What this does not test

      • The runtime. Not here, not reachable from here, not affected by anything you submit. This page tests one check.
      • Whether the caller asks. The most honest weakness in any guard is that it only helps if the code path consults it. A guard that is correct and unconsulted refuses nothing. That is a wiring problem, and no amount of clever input will reveal it from here.
      • Judgment. The guard checks whether a proposal is well-formed and correctly scoped. It cannot tell you the proposal is a bad idea. A conformant, properly scoped, strategically wrong action passes. That checker does not exist yet.
      • Cryptography. Nothing on this page attacks SHA-256. You cannot forge the digest, which is exactly why the interesting attacks all go after what feeds it.

      This runs a demonstration policy, not the production one, so probing it maps a demo table rather than the real guard. There is no bounty and this page takes no submissions: the receipt is the evidence, and it verifies without any of this code.
